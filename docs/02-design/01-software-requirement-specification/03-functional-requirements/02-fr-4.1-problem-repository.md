# FR §4.1 — Problem Repository

*Stores, retrieves, versions, and validates benchmark Problem Instances.*
*Source: MANIFESTO Principles 4–7.*
*Use Cases: UC-04.*

---

## FR-01

**The system MUST store Problem Instance records conforming to the schema defined in `docs/03-technical-contracts/01-data-format/02-problem-instance.md`, including all required fields: `id` (UUID), `name`, `version`, search space descriptors, objective specification, evaluation budget, landscape characteristics, and provenance.**

- **Priority:** MUST
- **Source:** MANIFESTO Principles 4, 7
- **Accepted when:** A `ProblemInstance` with all required fields is stored and retrieved without data loss; a registration attempt missing any required field is rejected with a `ValidationError` that names the missing field.
- Connects to: `docs/03-technical-contracts/01-data-format/02-problem-instance.md`; `docs/03-technical-contracts/02-interface-contracts/02-problem-interface.md`

## FR-02

**The system MUST validate Problem Instance completeness on registration: `dimensions` must equal `len(variables)`; variable bounds must be valid (lower < upper for continuous); all required fields must be present. Invalid submissions MUST be rejected with a specific error message identifying the violation.**

- **Priority:** MUST
- **Source:** MANIFESTO Principle 7
- **Accepted when:** Each of the following raises a `ValidationError` whose message identifies the specific violation: (a) `dimensions=2` with `len(variables)=3`; (b) a `ContinuousVariable` with `lower=1.0, upper=0.5`; (c) a record with `name=None`.
- Connects to: `docs/03-technical-contracts/01-data-format/02-problem-instance.md` validation rules

## FR-03

**The system MUST support Problem Instance versioning — modifying a Problem Instance produces a new version rather than overwriting the existing record. A Study references a specific version; that version MUST remain retrievable for the lifetime of the Study.**

- **Priority:** MUST
- **Source:** MANIFESTO Principles 6, 21
- **Accepted when:** Modifying a stored `ProblemInstance` produces a new record with a distinct `id`; the original remains retrievable by its own `id` and carries `superseded_by` pointing at the replacement. `version` is descriptive metadata for display and citation, never an addressing key (ADR-020).
- Connects to: `docs/03-technical-contracts/01-data-format/02-problem-instance.md`; `docs/05-community/02-versioning-governance.md`

## FR-04

**A Study MUST reference Problem Instances by identifier only, and every referenced entity MUST remain byte-identical for the lifetime of the Study.**

- **Priority:** MUST
- **Source:** MANIFESTO Principle 21; ADR-020
- **Accepted when:** `get_problem(id)` returns the same record at any later time, including for deprecated entities. Registering a revision creates a new entity with a new identifier and sets `superseded_by` on the old one; the Study continues to resolve to the entity it referenced. Cross-entity rule CV-018 rejects a Study referencing an unresolvable identifier at lock time.

> **Rewritten by [ADR-020](../../02-architecture/01-adr/adr-020-entity-versioning-immutable-entities.md).** This requirement previously demanded a `VersionMismatchError` when a Study declared one entity version and the registry held another. Under immutable entities that situation cannot arise, and `VersionMismatchError` was never part of the error taxonomy.
- Connects to: `docs/03-technical-contracts/01-data-format/04-study.md` (Study), `docs/03-technical-contracts/01-data-format/02-problem-instance.md` (Problem Instance)

## FR-32

**At `lock_study()` the system MUST reject a Study plan containing fewer than 5 Problem Instances with a `ValidationError` naming rule D-1 and the count found, unless the Study declares `study_type = "exploratory"`.**

- **Priority:** MUST
- **Source:** MANIFESTO Principles 4, 5; ADR-009 D-1
- **Accepted when:** (a) `lock_study()` on a plan with 4 Problem Instances raises `ValidationError` naming rule D-1 and the count found; (b) the same plan declared `study_type = "exploratory"` locks successfully, and the shortfall appears in the limitations section of both Reports; (c) a plan with 5 Problem Instances locks without a D-1 message.
- Connects to: `docs/02-design/02-architecture/01-adr/adr-009-problem-instance-diversity-requirements.md` D-1; `docs/04-scientific-practice/01-methodology/02-statistical-methodology.md` §3.4

## FR-33

**The system MUST validate that a Study plan's Problem Instance set covers at least 2 of the 3 dimensionality ranges (low: ≤5, medium: 6–20, high: >20) AND includes at least 1 instance with `objective.noise_level = "stochastic"` and at least 1 with `objective.noise_level = "deterministic"`. Failure on either check MUST raise a `ValidationError` at `lock_study()`. Exploratory Studies are exempt.**

- **Priority:** MUST
- **Source:** MANIFESTO Principles 5, 6; ADR-009 D-2, D-3
- **Accepted when:** (a) `lock_study()` on a Study whose 5 Problem Instances all have `dimensions` in [2, 4] raises `ValidationError` naming rule D-2; (b) a Study with no stochastic Problem Instance raises `ValidationError` naming rule D-3; (c) a Study spanning 2 dimensionality ranges with at least 1 stochastic and 1 deterministic problem locks without a diversity message; (d) an exploratory Study, declared by `study_type = "exploratory"`, is exempt from both checks and carries the shortfall into the Report limitations instead.
- Connects to: `docs/02-design/02-architecture/01-adr/adr-009-problem-instance-diversity-requirements.md` D-2, D-3; `docs/03-technical-contracts/01-data-format/02-problem-instance.md` (`dimensions`, `objective.noise_level`)
